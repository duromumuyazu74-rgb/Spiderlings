## 深入调查结论

### 敌人：先衡量有效遭遇和任务接续

test.85 已有大型场地、3×3 核心、可信原生共享感知、诱敌六回合无进展后的主动施压、核心内付费施工、Recovery 接力和持续巡猎。test.83 的双版本对照已经证明核心内等待时能够完工并捕获；堵工位、眩晕、击杀工人可以有效反制。这些成功反制不应统计成 AI 失败。

缺口在于普通玩家主动从入口走到出口的体验。test.85 的 22 图、6,600 世界回合是 Sneak1000 玩家旁观下的 NPC 生态记录，不能说明玩家会进入多少次有意义的围捕，也不能估计完整通关难度。

下一轮先做两版各 6 个固定种子的小样本诊断，覆盖窄道、回环和多入口房间；同 seed 固定面板、装备、资源并比较策略。记录“识别 → 合法接近 → 付费工作／攻击 → Capture／Recovery → 玩家应对 → 恢复职责”的事件和中断原因。

| 情景                  | 关键观测                                                               | 触发修改的证据                                               |
| --------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| 正常赶路与主动绕路    | 路线增量、首次危险可见时间、活跃场地、迫使玩家改变路线／消耗资源的时点 | 场地长期不接触实际路线且无有意义压力时，再检查选址与诱敌路线 |
| 靠近、退走、转角遮挡  | 个人识别、报告年龄、诱敌自身进展                                       | 四回合情报不失效，或工人工作仍替诱敌无限续命，才是退化       |
| 堵住工位再离开        | 阻挡期间无非法施工，离开后的首个合法工作及保存进度                     | 阻挡消失后仍可复现职责丢失；不消除堵工位本身的收益           |
| 眩晕／击杀工人、破网  | 控制结束、替代成员可达性、付费修补与撤退空间                           | 已有合法工人仍持续无原因空转，或出现免费补建                 |
| Mage 与 Maid 交战后   | Maid 死亡与控制分列，战斗结束到回岗／寻敌的时间                        | 两击杀是成功；只调查清场后任务接续，不削弱伤害强迫包裹       |
| Recovery 1/2/4/8 来源 | 真实命中、项圈准入、接线支付、LOS、断根、剪线和撤离资源                | 先检查玩家能否辨认有效来源；八来源极难是既定要求             |

收益是把改动落在真实失效的环节；代价是需要保存事件轨迹和对照样本。没有新反例之前，不再改全局伤害、场地尺寸、来源上限或逃脱数值。

### 楼层：复用现有任务标记

本次在 test.85 最终包的两个版本分别生成侵袭与猎场，调用真实原生 `drawminimap.QuestMarker`：即使 Vision=0 且 Fog=0，原始任务巢仍有小地图红点；额外通过原生召唤加入的普通巢对照不显示红点（未在本探针重跑完整 Tunneler 筑巢 AI）。只剩一个原目标时，红点保留，进度分别为 4/5 与 2/3。主地图目标图案仍需要当前视野，小地图关闭或视口裁切时不保证看见该红点。

因此首选玩法改进是补已有进层说明与未完成时的楼梯提示：目标只包括最初标记的巢；开启小地图可查看任务标记；后建普通巢不增加目标。不增加地图记忆、自动寻路或每回合全图扫描。

候选文案：“摧毁本层最初标记的目标巢穴即可下行。开启小地图后，可查看这些巢穴的红色任务标记；后来筑起的普通巢穴不计入目标。”实际用语仍需中英文 UI 检查，不能把所有原生任务红点都宣传成巢穴。

验收为双版本 × 两主题 × 中英两语言，共 8 组进层／楼梯提示；原目标剩一巢、普通新巢、关闭小地图、远目标裁切、侧房往返和存读档均不改变原目标配额。收益是低成本降低误解；取舍是提示变长，未实测前不承诺节省找巢时间。

### 猎场取消：有真实损失，但现有行为是安全降级

test.85 既有每版 75 图的指定主题生成样本中，猎场每版 35 个满足自然资格的样本各有 3 次取消，即该有限样本的 8.57%；另有每版 10 个强制 Hell 对照。不能将其解释为自然选择概率或全局取消率。

本轮用最终 test.85 ZIP 将历史 6 个失败 seed 在两版全部重放，12 图执行成功，各自历史的 3 处取消均重现，跨版本的 6 个对照成功。观察到早期 anchors、原巢数不足或场地数不足等诊断；部分首轮失败又被已有回退挽回，因此首轮诊断不等于最终失败原因。

后续只在 scratch 比较有界替代组合。必须同时保留三巢、至少两场地、必要队伍、用户人口上限、保护点和可达性。记录中位／p95 生成耗时；不默认增加五次地形尝试，不降低至单场地，也不因取消而新增奖励。只有找到保留全部约束的合法替代解，才考虑修改选址。

## 特殊楼层人口方案

用户已选此方向深入。下面的方案是下一阶段设计，不属于本轮已交付运行时修改。它不重新讨论 Mage、持续巡猎、三巢／五巢、多场地和付费施工等已有决定。

当前 `SpiderlingsInfestation.js` 调用 Hunting Grounds 查询人口计划和初始化两支队伍，而 Hunting Grounds 初始化又回调 `Infestation.openNestClearing`。同时 Hunting Grounds 拥有两个主题的原生初生、游荡与预设保护规则。一个人口决定需要跨主题来回追踪，这是已确认的架构负担；目前没有因此证明新的玩家可触发 bug。

深化目标是让人口 module 的 interface 表达完整请求和结果，把预算、队伍原子性及失败清理纳入同一 seam；两主题作为真实 adapter 保留各自的巢分布、地图地形与逃离目标。depth 必须来自 caller 不再编排半成品，而不是新增文件。

Deletion test：必须删掉 `Infestation → HuntingGrounds → Infestation` 同次初始化调用环，以及两主题为了正确出生必须共同知道的清理顺序。保留两主题的独立目标与布局测试。若最终只是一个转发预算函数的 shallow module，则不实施。

### 已确认的第一阶段范围

用户确认保持现有行为：先统一实体、配额和登记清理，地形恢复另立方案。这里的完整队伍是“必要成员全部出生，或本次成员全部撤销”，不是整张地图、随机序列或实体 ID 的事务回卷。

静态追踪证实：侵袭先成功创建五巢，发布状态并清地，再进入两支驻军的创建；后段失败会撤子体和巢、取消主题，但不还原 Grid、TilesSkin、TilesMemory。猎场普通驻军路径较晚清地，早期 Layout 又有独立的地形尝试和预留释放。现有五次地形重试内部还原与最终主题取消不同。第一阶段应锁住这些差异，不统一成新的地图恢复规则。

### 三种 interface 比较

| 方案                                      | caller 需要知道的事                                                                                 | depth / locality                                                   | 主要取舍                                                                                       |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| A：初始化配额、完整队伍出生、缺员角色查询 | 主题先决定巢／地形，把已选巢和场地交给人口 module；按原时序登记目标／清地，按完整人口结果完成或取消 | 预算、角色、出生清理集中；地形与目标留原主题，能删除跨主题开地回调 | 有三个入口，但每个都有现有消费者；目标巢失败清理由主题拥有                                     |
| B：公开 plan → commit                     | caller 需要保证计划只用一次、同图且紧接提交，中间不能出生或推进世界                                 | 计划可查看，失败阶段清楚；公开顺序仍需 caller 维护                 | 当前没有编辑器或跨回合预览消费者，外露两阶段的收益不足；计划不能假装已经证明开地后的所有位置   |
| C：包住完整原生初生流程                   | caller 给生成上下文与原生后续调用，一次处理主题准备和人口选择                                       | 常见调用最少，选择上下文的 finally 可集中                          | 容易同时接管布局、取消、原生包装顺序和统计；取消主题前后的 selector 时序更易改变，首批风险较大 |

建议采用 A，将 B 的阶段划分与错误诊断保留为私有 implementation；不要公开可持久化计划或事务框架。C 的完整生成编排暂不合并，先用集成测试固定已有原生顺序。三个方案的原稿保存在旧审查 checkout 的 `.scratch/population-design-{minimal,staged,common}.md`。

### 推荐 interface 草案

使用普通 JavaScript，名字为讨论草案；不为方案新增运行时文件或存档字段。

```js
const capacity = Spiderlings.Population.prepareFloor(theme);
// 在原人口 plan 发布点创建／复用 plan，返回 { cap, available }。
// 这是有写入语义的初始化，不预约实体位置、不消费 RNG。

const result = Spiderlings.Population.seedCrews({
  kind: theme,
  nests: selectedCoreNests,
  spawnPoints,
  sites: plannedHuntingSites,
});
// 成功：{ ok: true, coreNestIds, coreIds, patrolIds }
// 普通失败：{ ok: false, reason }

const missing = Spiderlings.Population.missingRoles(nest);
// 只读缺员名册；普通巢／旧名册继续进入现有增援规则。
```

`prepareFloor` 由主题在原 `createPopulationPlan` 的位置调用，明确创建／复用当前人口计划，再返回预算。现有 `SpiderlingsPopulationPlan` 在目标巢召唤和清地之前就可能被 native hook 观察，不得延迟到 `seedCrews` 成功后才写入，主题取消仍负责撤销。纯预算计算留在 implementation 内，供原生额度检查共同使用。相比只读 `budget` 草案，这样既维持三个入口，也明确了必须发生的写入与顺序。

`seedCrews` 同步完成必要队伍创建、坐标／数量核验、母巢归属与角色登记，实际执行前重新检查余量。侵袭需要两支六人队，猎场三支六人队；猎场额外巡逻保持完整六人或零人，巡逻失败不能误取消已经成立的主题。两个主题直接调用该入口，人口 module 不回调主题的清场函数。

不能把玩家 Perk 的六人队与这里的巢队合并成一张成员表。当前巢队为 Spinner×2、Jumper×1、WebCaster×2、Mage×1；Perk 队含 Tunneler，编制、距离和一次性状态不同。首阶段不迁移 Perk、保底 Mage、死亡爆怪或整套巢增援循环；它们继续消费统一配额。

`missingRoles` 只集中现有六人名册与同种不同角色的缺位规则。巢增援的正时间计时、原生感知／报警、概率、配置权重、每巢活体额度、Tunneler 终身额度和逐半径尝试留在 Encounters。原生游荡保留原生调度，只复用共同预算与人口选择规则。否则人口 module 会变成不必要的全局蜘蛛调度器。

### 写入归属与失败结果

| 内容                                      | 谁拥有                  | 第一阶段契约                                                                               |
| ----------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------ |
| 人口预算、完整子队、母巢名册和角色        | Population              | 本次新增实体登记在出生账本；失败仅清理本次对象及本 module 未完成登记，不按全图物种批量删除 |
| 原目标巢、目标进度、取消主题及 Key escape | 各主题                  | 原目标数量和 ID 语义保留；人口失败后沿现有取消路径处理本次目标巢                           |
| 巢选址、清场、早期 Layout、预约释放、导航 | 各主题／Layout          | 保持各自顺序与已有失败后地形结果；不假定 release 是 undo                                   |
| 原生初生／游荡选择的临时上下文            | 人口选择 implementation | 保持现有进入顺序，用 finally 恢复上下文；不让普通图继承主题过滤                            |
| 保存和重入                                | 原有地图状态            | 不重新出生、不补齐历史队伍、不增加 schema；已有兼容字段及老四人名册仍可读                  |

普通预算、空间或出生失败返回可观察的失败原因；原生抛错仍按错误处理，不包装成正常“空间不足”。清理效果必须检查，不能只调用删除就宣称无残留。原生拒绝删除、第三方副作用和异常恢复先写故障注入证据，再决定最窄的处理；不引入全局回滚器。

特别要保留失败路径的包装时序：当前 Hunting Grounds 外层可能先建立 initial selector，再进入 Infestation 内层；后者可能取消主题。若重构提前取消再重新判断主题，会改变原生后续出生的筛选。先记录这个路径的现状，再判断是否另立 bug；不能将变更藏在“纯提取”内。

### 迁移批次与验收

1. **先固定行为。** 通过生产入口运行两主题的成功、低预算、必要队伍中段失败、可选巡队失败和内层取消。分别记录实体、人口登记、目标、地形及原生 selector；不以整张 map 深相等要求不存在的地形恢复。
2. **集中预算与名册。** 保留旧外部名称的短期转发以避免同时改 hook 顺序；统一配额解释与缺员角色，验证全局 0、主题预算、盟友占额、既有超额、旧名册和显式零权重。
3. **集中完整队伍出生。** 把同一规则放到 `seedCrews`；侵袭自己选择首巢和最远巢并按旧时机清场，删除对 Hunting Grounds 的人口调用及回调。随后迁移猎场必要队与可选巡队。不提前或延后已可被原生 hook 观察的状态发布，除非有独立证据和变更记录。
4. **删除重复编排。** 所有调用者迁完后删除旧转发、重复成员表与重复清理分支。保留主题布局／逃离测试，将迁移后只断言内部函数调用顺序的测试替换成 interface 结果测试。
5. **双版本验收。** 新版本最终 ZIP 跑完整门禁，另用固定成功／取消 seed 比较原生出生轨迹；差异先查 RNG 消费、包装顺序和保护规则，不直接修改期望值。完成后才评估是否扩展到其他出生来源。

重点故障矩阵：必要成员的每个出生位置分别返回空、错位、额外实体或抛错；已有 NPC／盟友／受保护预设必须保持，本批无残留、无额外击杀／掉落／目标进度。巡逻失败只撤巡逻，核心仍成立。两主题都测真正完整调用链，避免只加载 Infestation 而漏掉后段驻军路径。

验收还包括：父 ID 与角色准确；读档、侧房往返与重复初始化不补生；缺员同种角色正确；旧四人巢按旧规则；被取消地图使用当前规定的普通 escape；地形结果与基线一致。性能记录相同 seed 的中位及 p95 生成耗时，没有重复整图扫描或新增全局每回合工作。

这一方案的收益以删除跨主题初始化环、减少配额真相来源、故障在一个 interface 上可复现衡量，不以文件变少或行数变短衡量。地形恢复、重选布局和数值调整保持独立后续范围。
